## 개념 지도 — 막히면 여기로

```
이벤트 수집 ── HTTP 설계(202, fail-open) ── 백프레셔 ── 재시도 폭주
     │
     ├─ Kafka ── 파티션/키 ── 컨슈머 그룹 ── 전달 보장 ── 재처리
     │
     ├─ 스트림 처리 ── 이벤트타임 ── 워터마크 ── 윈도우 ── 상태/TTL ── 체크포인트
     │
     ├─ 원본 적재 ── 컬럼 포맷 ── 파티셔닝 ── small files ── 테이블 포맷(Iceberg)
     │
     ├─ 배치 ── 멱등성 ── 전범위 중복제거 ── 정산
     │
     └─ 정합성 ── 람다 아키텍처 ── 대사 ── 차이의 원인 분해
                         │
                         └─ 트랜잭션 경계 ── Outbox ── CDC
```

## 면접에서 자주 나오는 질문 (답의 뼈대)

**Q. 이벤트 유실을 어떻게 막나?**
수집에서 fail-open(로컬 파일) → Kafka 복제 → 컨슈머는 처리 후 커밋(at-least-once).
유실 대신 중복을 받고, 중복은 `event_id` 기준으로 세 층에서 제거한다.

**Q. 정확히 한 번(exactly-once)은 왜 안 쓰나?**
Flink 의 exactly-once 는 Kafka→Kafka 구간에서 성립한다. 종착지가 Redis/S3/PostgreSQL 이라
싱크까지 원자적으로 묶으려면 2PC 가 필요하다. 대신 **배치를 멱등**으로 만들어
"몇 번 돌려도 같은 결과" 를 얻는 쪽을 택했다.

**Q. 실시간 값과 정산 값이 다르면 뭐라고 설명하나?**
다른 게 정상이다. `확정 = 실시간 + 지연반영 − SSAI − 장기중복`.
대사 테이블에 그 분해를 미리 계산해 둔다.

**Q. 파티션 키를 왜 그렇게 골랐나?**
`ad_request_id`. 광고 1편의 이벤트가 한 파티션에 모여야 SSAI 판정 같은 처리가 로컬해진다.
`campaign_id` 는 핫 파티션 위험이 크다. 집계는 어차피 Flink 가 다시 키잉한다.

**Q. 워터마크 지연은 어떻게 정하나?**
지각 이벤트 비율과 집계 지연의 교환이다. 실제 도착 지연 분포(`server_ts - event_time`)의
p95~p99 를 재서 정한다. 이 저장소는 10초.

**Q. Outbox 를 쓰면 중복이 생기는데 왜 쓰나?**
DB 커밋과 Kafka 발행이 원자적일 수 없기 때문이다. 유실(발행 누락)보다 중복이 낫고,
중복은 downstream 에서 제거 가능하다.

**Q. 트래픽이 10배가 되면 어디부터 손보나?**
Outbox 워커(단일·잠금 없음) → Collector 인스턴스 → Flink 상태 백엔드 → 파티션 수 →
배치의 전체 재계산. 순서와 근거는 [04-scale-100m.md](04-scale-100m.md#5-순서대로-깨진다-부하를-올릴-때-나타나는-증상).

**Q. 광고가 실제로 노출됐다는 것을 어떻게 신뢰하나?**
클라이언트 비콘은 조작 가능하다. 그래서 (1) 픽셀에 HMAC 서명, (2) 정합성 분모는
서버가 확정한 `ad_response`, (3) SSAI 는 서버 경로를 우선 채택한다.

## 이 저장소가 일부러 축소한 것 (같이 알아 둘 것)

루트 README "10. 실제 운영과 다르게 단순화한 부분" 에 목록이 있다. 요약하면:

- 타게팅·빈도제어·입찰이 없는 광고 결정 (→ [03](03-ad-decision-api.md#4-지금-구현-vs-실제-광고-서버))
- 단일 브로커·단일 Redis·단일 Postgres (HA 없음)
- 스키마 레지스트리 없음 (JSON 직접. 운영이면 Avro/Protobuf + 호환성 규칙)
- 인증/인가·개인정보 처리 경로 없음
- 배치 스케줄러 없음 (수동 실행)

**"무엇을 뺐는지 아는 것"이 곧 무엇을 배워야 하는지의 목록**이다.
